# NotesApp STRIDE threat register

- TB1 means boundary 1 in the diagram: browser clients (Student, Teacher, Admin and the generic Browser) ↔ Flask.
- TB2 means boundary 2 in the diagram: Flask ↔ PostgreSQL. Flows 38–39 instead connect Flask and the shell/ping process; flows 42–43 connect Flask and static files, as specified by the flow list. They are not PostgreSQL queries or results.
- Audit logs, image backups, the Docker socket and spreadsheet execution are deployment or downstream context. They have no separate flow or boundary numbers in these two reference files.

S = Spoofing, T = Tampering, R = Repudiation, I = Information disclosure, D = Denial of service, E = Elevation of privilege.

| ID | Flows / scope | Type | Issue |
|---|---|---|---|
| TH01 | 1–4 | S, T, E | Credentials enter Flask in flow 1 and are concatenated into the login SQL in flow 2. An altered query may return another user's identity in flow 3 and establish that identity in the session cookie in flow 4, possibly as an admin. |
| TH02 | 4, 9, 13, 17, 21, 25, 29, 33, 37 | S, E | Flow 4 sets a Flask session cookie containing identity and a JWT. The published `SECRET_KEY` signs the session, separately from the JWT key. Someone knowing it could forge session identity or role data for subsequent cookie-authenticated requests, including the cookie option in flow 13. |
| TH03 | 13–16 | S, I | Flow 13 accepts either a Bearer JWT or a session cookie. The JWT verifier accepts `alg: none` and uses a weak published `JWT_SECRET`, so a forged Bearer identity could cause Flask to query a note in flow 14 and disclose it in flow 16. Teacher/Admin pages use the Flask session, not Bearer JWT authentication. |
| TH04 | 13–16 | I | Flow 14 selects by `note_id` without checking the authenticated user's ownership. A logged-in user can request another student's record in flow 13 and receive the grade and comment in flow 16. |
| TH05 | 17–20, 25–28 | I, E | The teacher-page query in flow 18 and export query in flow 26 are not restricted to classes owned by the current teacher. Their HTML and CSV responses in flows 20 and 28 can disclose other teachers' class records. |
| TH06 | 21–24 | T, E | Flow 21 supplies a note ID for an update, or student and class IDs for creation. The write in flow 22 checks neither teacher ownership of the target class nor authorization over the existing note, allowing changes outside the teacher's classes. |
| TH07 | 21–22 → 11–12 / 19–20 | T, I | A comment enters through flow 21 and is stored by flow 22. It is later returned in flow 11 or 19 and rendered without HTML escaping in flow 12 or 20. An actor with comment-write access could store a script that runs when a Student or Teacher views the HTML page. Flow 16 is JSON, not this HTML-rendering sink. |
| TH08 | 7–8, 21–24, 33–40 | T, E | Grade writes, user management and ping requests have no CSRF token checks; logout uses GET in flow 7. SameSite is not explicitly set ([Flask defaults](https://github.com/pallets/flask/blob/3.0.3/src/flask/app.py)). An attack depends on the victim browser sending its session cookie; an induced Admin ping request in flow 37 could trigger TH13. |
| TH09 | TB1; HTTP deployment | S, T, I | HTTP requests and responses cross the browser/Flask boundary. The Compose setup serves HTTP and the session cookie has no Secure flag. An attacker able to intercept that traffic could steal credentials or cookies, reuse a session, or modify requests and pages. |
| TH10 | PostgreSQL; image backups / deployment context | I | Passwords are stored directly and are also present in the image's password backup. Database or backup access can expose credentials. Current AES-GCM encryption limits disclosure of comments from a database-only read without the key; key or application-runtime access can still expose them. Listing `comment` in database-result flows does not mean it is stored in clear text. |
| TH11 | 1–4, 7–40; audit context | R | Login attempts are logged, but logout and sensitive reads lack user-level audit records. Grade logs omit old/new values and affected records; user management and exports are not logged. Ping logs the host without the actor. These are audit gaps in the listed operations, not additional numbered logging flows. |
| TH12 | 1–44; resource usage | D | HTTP requests can trigger database work, writes and exports, while logs continue to grow. There is no app rate limit or pagination, so repeated or large requests could exhaust service resources. Practical thresholds still need a load test; the static-file flows 41–44 are not database queries. |
| TH13 | 37–40, especially 38 | T, D, E | The Admin supplies `host` in flow 37. Flask concatenates it into a command executed with `shell=True` in flow 38, receives process output in flow 39 and renders it in flow 40. Someone with an Admin session could execute commands beyond ping to alter files or disrupt the service. |
| TH14 | 38; Docker deployment context | E | Code execution such as TH13's flow 38 occurs in a root container with the Docker socket mounted. If the attacker can use that socket, compromise may extend to the Docker Engine host and bind-mounted project files. Root inside a container alone does not prove host escape; Docker operations have no separate numbered flows in the baseline. |
| TH15 | 21–22, 25–28; spreadsheet use | T, I | A crafted comment is submitted/stored through flows 21–22 and included in the CSV download in flow 28 after the export query and result in flows 26–27. Formula evaluation happens if a Teacher opens that CSV in a spreadsheet, outside Flask, and depends on the application's settings. Comment encryption at rest does not neutralize exported formulas. ([OWASP](https://community.owasp.org/attacks/CSV_Injection)) |
| TH16 | 21–24 | T | Flow 21 carries the grade, student and class inputs. Before the write in flow 22, the app does not enforce a business grade range or verify that the chosen user is a Student enrolled in that class. A Teacher could store false academic records; non-null user/class IDs must still satisfy foreign keys. |
| TH17 | 4, 7–8, 12–16 | S, I | The JWT is included in the session in flow 4, exposed to the student's page in flow 12 and sent as Bearer authentication in flow 13. Issued tokens have no expiry. Flows 7–8 clear the browser session cookie but do not revoke a copied token, which can still be used at the API afterwards. |
